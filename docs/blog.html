Building Hypnos: memory for AI agents that sleeps on it

Nine versions in three weeks, every benchmark I ran, and the one where my newest version lost by ten points.

I run a lot of coding agents, often five or six opencode sessions and a few Claude Code sessions at the same time, on a laptop with 7.5 GB of RAM. Every new session starts knowing nothing about the ones before it, so the same ports, folders and decisions get explained again.

I wanted a memory that saves only what was actually said, with a quote to prove it, hands back as little text as possible, and lets me see where every memory came from. So I started writing my own. It's called Hypnos now. For most of its life it was called agentmem, and you'll see that name in older results.

The idea: copy how people remember

People don't save everything they hear as a permanent fact. During the day you notice things. At night, while you sleep, your brain sorts them: what mattered gets kept, what changed gets updated, the rest fades. The next morning you don't replay the whole day. Something reminds you, and the right memory comes back.

Hypnos does the same thing in three steps.

Awake. Every message, tool call and result goes into a raw log the moment it happens. Nothing waits for the context window to fill. Secrets such as API keys are scrubbed before anything is written.

Asleep. When a session ends, or goes quiet for ten minutes, a small and cheap model reads the log and writes down short facts. Each fact has to quote the exact line it came from. If the quote can't be found in the log, the fact is thrown away. A System One model (more on that below) then checks every fact against its quote, decides whether it replaces an older fact (you changed the port from 8080 to 7439), and files it under a topic. Each topic gets three summaries: one sentence, one paragraph, one page.

Remembering. When you send a message, Hypnos picks the smallest piece of memory that answers it. A broad question gets a topic summary. A precise question ("which port does staging use?") gets the exact facts with their quotes. Most messages need nothing at all, and get nothing.

Why a System One model

Most of the decisions in a memory system are yes/no or pick-one questions. Does this quote support this claim? Does the new fact replace the old one? Is this memory relevant to the question? Asking a chat model these costs a full LLM call each time. A System One model, like Jev or the open-weights Laya, answers them in one fast step instead of writing text. In my tests Jev made these calls 7 to 15 times faster than the chat model and agreed with it 76 to 90% of the time. Without one, Hypnos still works. The memory model you pick does those checks while saving, a little more accurately in places, but with more tokens.

Benchmark 1: my own coding sessions

The first test used my real work. I took 15 Claude Code sessions and wrote 60 questions about them, each answerable by an exact quote, such as "what port did we move the dev server to?" Benchmark 2: LoCoMo, against Mem0 and GBrain

LoCoMo is a standard test for long-term memory: ten long conversations between two people, with questions about them. I used 200 questions, 50 in each category: single-hop (one fact), multi-hop (join two facts), temporal (when something happened) and open-domain (needs some reasoning).

Every system got the same conversations and the same answering model. The answers for each question were shown to a grader from a different model family, side by side and without names, so it couldn't favour one system.

The time v0.9 lost by ten points

For v0.9 I wanted better answers about dates. I changed three things. The model that writes facts would see the date on every line of the log. It would turn "yesterday" and "next Friday" into real dates. And the answering model would be told that a later message overrides an earlier one.

It sounded sensible. It scored 47%, against 57.5% for v0.8 in the same run (Muse Spark 1.3 answering, Claude Haiku 5.5 grading). Dates, the thing I was trying to fix, dropped from 80% to 60%.

v0.8's own answers were graded again in each run, and scored 57.5% in the first and 60.5% in the second; only scores from the same run are compared.

I went through the losses one by one. In 14 of the 26 questions v0.9 lost, it answered "not mentioned": the fact had never been saved. With the extra date work in its instructions, the small writing model saved 93 facts from a conversation where v0.8 saved 160. The "later message overrides" line did its own damage: in a chat between two friends, a newer message doesn't cancel an older one, so the answering model threw away correct facts.

I took all three changes out and ran it again. The fixed v0.9 tied v0.8 exactly, 121 correct answers each, and each got 8 questions right that the other missed. The rule I took from it: nothing goes into the instructions of the writing or answering model until it has beaten the previous version on the benchmark.

What v0.9 adds

v0.9 doesn't remember better than v0.8. It makes the memory something other people can actually use.

One-line install. One command on macOS, Linux or Windows. It downloads what it needs, finds Claude Code, opencode, Codex, Gemini CLI, Cursor and Windsurf, and connects to each one. A coding agent can run the install itself: there are exact steps for agents in the install guide.

Your choice of model. Nothing is tied to one model. Setup lists every model your machine can use, free ones included, and the person or agent installing it picks the best value. If a model goes down or runs out of quota, the next one takes over.

Quiet. Memory runs only while one of your agents is open, with no windows, and switches itself off about a minute and a half after you close the last one. On machines with less than 12 GB of RAM it saves one model call at a time, so the computer doesn't lag.

/memory-cleanup shows duplicates, unused facts and stale facts by topic in under a second. Delete by number or by topic.

Many sessions at once. Each session is told what the others in the same project are doing, and that their tasks aren't its own. It never hands your own current conversation back to you as a "memory".

It doesn't remember refusals. "The assistant couldn't do X" is never saved, so a later session won't refuse the same thing because a memory told it to.

Things I tested and didn't ship

I rewrote the whole v0.8 engine in Rust to see what it would buy. Same accuracy (55% for both), search 3.0 seconds instead of 3.8, cold start 3.9 seconds instead of 7.8, about the same RAM. Most of the time goes to waiting on models over the network, not to running code, so the faster language doesn't help much. The Rust version is kept for later, once the design stops changing every week.

What these numbers don't show

With 200 questions, a grader re-marks a few answers differently between runs; I measured about ±3 points of noise. Published results for Mem0, Zep, Letta and others use different answering models, graders and question sets, so compare them only loosely with mine. Open-domain questions are still weak for every system I tested, and multi-hop is where I'm working next.

Try it

macOS and Linux:

curl -fsSL https://agent-memory-architecture-chi.vercel.app/install.sh | sh

Windows (PowerShell):

irm https://agent-memory-architecture-chi.vercel.app/install.ps1 | iex

Restart your agent afterwards and keep working. The code, the install guide and the steps for coding agents are on GitHub. Every benchmark run, with per-question results, is on the benchmarks page.
