Memory that sleeps and shows its evidence

Architecture for a long-running LLM agent. It keeps a layered memory, holds every topic at three sizes (small, medium, big), can always open the evidence behind what it remembers, and tidies that memory while it is offline. Jev makes every small typed decision; an LLM does the writing.

See the architecture JSON spec for agents
Awake: work, log, recall Asleep: consolidate

What changed in v0.8, v0.7, v0.6, v0.5, v0.4 and v0.3 (all tested)

v0.8, recall redesigned around Jev, tested on LoCoMo in section 10 (55% with ~600 tokens of context, first):

  1. Code gathers, Jev decides. Code collects candidates from every layer: the three summary levels, hybrid-ranked facts and raw messages, and all facts about the people named. Jev then answers dozens of typed questions in parallel (free, one round).
  2. Question routing. Jev classifies each question: overview, single fact, list, when, or exact value.
  3. The summary ladder is back for overviews. The smallest summary level that answers (small, then medium, then big) is the whole context.
  4. Per-item evidence gating. For every candidate fact and message, Jev judges whether it is part of the answer; only those are sent. Lists keep every relevant item.
  5. Answerable check. If the kept evidence does not answer the question yet, on-topic items are added. Result: ~600 tokens per question, 5× less than v0.7.

v0.7, recall only, tested on LoCoMo against Mem0 and GBrain in section 10 (53%, first):

  1. Evidence first. Hybrid search (keyword + meaning, fused with RRF) over facts and raw messages is the first recall step; topic summaries only orient.
  2. Meaning search over raw messages. Every message is indexed locally (bge-small), not just facts.
  3. Entity gather. Every fact about the people and things named in the question is pulled in, most relevant first (list and multi-hop questions).
  4. Stricter gate. Recall stops early only when the evidence itself answers the question (R15 for every question).

v0.6, tested in section 10 (96% on coding sessions):

  1. Exact-value rule. Jev flags questions that ask for an exact value; those may only stop on evidence (fact quotes, anchors, original log), never on a summary's wording (R15).
  2. The gate judges evidence. For exact-value questions the "enough?" check sees only facts and log snippets.
  3. Log snippets up front. Exact-value questions get the best original-log snippets from the first step.
  4. Lean deep steps. The original-log and whole-history steps drop the big summaries, cutting the hard questions from ~9,900 to ~5,800 tokens.
  5. Meaning search. A small local embedding model runs next to keyword search on every layer.

v0.5, tested in section 10 (92%, level with keyword search):

  1. Original log layer. Each topic zooms small, medium, big, then its own original log before any whole-history search.

v0.4, tested in section 10 (88%):

  1. Keyword search on every layer. Small, medium, big, facts and the original log are searched at the same time and the rankings fused to pick the topic. In the test this lifted accuracy from 83% to 88%.
  2. Keyword anchors. Each summary keeps up to 30 exact identifiers from its facts, so an exact value can be found even in a small summary.
  3. Topic splitting. Topics with more than 24 facts split into chronological parts.

v0.3, tested in section 10 (83%):

  1. Jev has two roles. The gate advises while awake; the judge answers bounded questions during sleep (verify, link, topic, entity, contradiction type, importance, drift). 17 typed questions in total, section 6.
  2. Decision log and shadow mode. Every Jev answer is logged. Each question starts in shadow next to the LLM and goes live only after it agrees often enough.
  3. Facts have a validity window. valid_from and valid_to, so "what was true in March?" has an answer and not every contradiction is a replacement.
  4. Entities. A table of people, files, symbols, services and configs. Mentions are resolved to entities during sleep.
  5. Trust order. CLAUDE.md, then what the user said, then what was observed, then what the agent inferred (R11).
  6. Readable export. memory.md is written every sleep. Your edits to it come back in as user facts.
  7. Code-aware evidence. Facts can cite code:path@commit#L40-60, are marked stale when that code changes, and there are new kinds: convention, command, gotcha, failed approach.
  8. Hybrid search. Keyword (BM25), vectors and a path/symbol index, boosted by the files and entities in play.
  9. Incremental rebuilds. Big is rebuilt only when its facts change; Medium and Small only when that change matters at their size.
  10. Several sessions at once. Per-session logs and watermarks, one writer at a time on shared memory, facts scoped to a git branch until merge.
  11. Sleep budget. Must-run steps always finish; deferrable ones move to the next sleep when the budget runs out.

v0.2 (25 Sep) fixed 12 design mistakes in v0.1: forgetting, confidence, session ids, core bootstrap, nap duplicates, fact ids, supersession, summary citations, recall start, topic ladder, privacy path, housekeeping.

01

Overview

Two modes and one shared store. While awake, the agent works, logs everything, and recalls memories on demand. While asleep, a batch job turns the not-yet-consolidated part of its session's log into checked, linked, layered memories. Jev makes the small typed decisions in both modes; an LLM does everything that needs writing.

Memory layers

Memory is organised two ways over the same facts. By time answers "what happened, and when". By topic answers "what do I know about X". Both are small at the top and exact at the bottom, and recall goes down only as far as the question needs.

A calendar day can hold several sessions, since sleep also starts at a context threshold, at task end or when idle. Every summary sentence cites the fact or child ids it came from.

3.2 By topic: small, medium, big, original log

Every topic the agent works on (for example "auth", "billing", "deploy") is kept at three summary sizes, with its own original log underneath. Every summary carries keyword anchors, the exact paths, IDs, versions and settings from its facts, and recall keyword-searches small, medium, big and the original log at the same time to find the right topic. It then reads the smallest layer first and zooms in only when that isn't enough; when a summary has paraphrased an exact value away, the next step is the topic's own log, not a search of the whole history. Topics group entities, so "auth" knows it is about src/auth.ts, validateJwt and the auth service.

All three summaries are written from the same facts, each with its own token budget, so a mistake in Big cannot flow into Medium or Small.

The original log is never rewritten. It is the source every fact was checked against, and each fact points to its exact span in it.

Rebuilt only when needed. Big is rewritten when one of its facts changes. Medium and Small are rewritten only when a fact they cite changed, or Jev judges the change matters at their size.

3.3 Trust order

Every fact records where it came from. When two facts disagree, the more trusted source wins, and a less trusted fact can never silently replace a more trusted one (R11).

1. CLAUDE.mdhuman-authored project rules; read first on wake
2. Userwhat the user said, pinned or corrected, incl. memory.md edits
3. Observedtool output, test results, code
4. Inferredthe agent's own reasoning and predictions

  • kind: event, prediction, outcome, decision, lesson, belief_revision, and for code work convention, command, gotcha, failed_approach.
  • source: user, observed or inferred. CLAUDE.md is read directly and sits above all of them.
  • evidence: log:a-b, code:path@commit#La-b or user:memory.md@hash. evidence_status: ok, stale (the cited code changed) or deleted (privacy path).
  • valid_from / valid_to: when the fact was true. A replaced fact gets a valid_to; a fact that is only true in some contexts gets a narrower scope instead.
  • scope: repo and branch. Facts from an unmerged branch are only recalled on that branch.
  • importance: Jev score level 1 to 5 (trivial, minor, useful, important, critical).
  • confidence on an episode: (claims_extracted − claims_rejected) / claims_extracted. On a summary: share of sentences whose citations pass the drift check.
  • status: active in the index, archived out of the index but reachable through its parent, superseded replaced by a newer fact.

Link types: same_entity, supports, contradicts, supersedes, about_topic. Entity types: person, file, symbol, service, config, project, other.

05

Flows

Six procedures make up the whole life of the agent. J marks a step where Jev answers.

5.1 Wake

  1. Read CLAUDE.md (or the project's equivalent). It is the top of the trust order.
  2. Import edits the user made to memory.md since the last export; each becomes a user fact.
  3. Load the core node and the last wake_session_summaries (3) session summaries.
  4. Load the small summary of each topic the wake note names, plus any other topic Jev judges relevant to the plan. J
  5. Load the latest wake note last. Stable parts come first so the prompt prefix stays cacheable.
  6. Start the agent loop with only this context. Everything else comes through recall.

5.2 Awake loop

  1. Receive input, redact it locally, and append it to the session's raw log.
  2. Ask the gate whether memory is needed and where to start. If yes, call recall with that start level and the current files, entities and branch. J
  3. If a recalled fact will drive a decision, open its evidence first (R7). For code: evidence that means reading the current lines (R13).
  4. Act, and append the redacted action and result to the raw log.
  5. Afterwards and off the main path, the gate judges which recalled memories changed what the agent did; those get useful_count + 1. J
  6. Check should_sleep: hard thresholds in code, "is this a task boundary?" from the gate. If true, finish the step cleanly and hand over to the consolidator. J

5.3 Recall

Pseudocode
def recall(query, token_budget, context=None):          # v0.8: code gathers, Jev decides
    # 1. gather candidates from every layer (code only, milliseconds)
    facts   = rrf(bm25(query, layer="facts", k=30), vectors(query, layer="facts", k=30))[:25]
    msgs    = rrf(bm25(query, layer="original_log", k=30), vectors(query, layer="original_log", k=30))[:15]
    people  = entities_named_in(query)                    # "Melanie", "the router", "app.py"
    about   = rank_by_meaning(query, facts_about(people))[:30]   # everything about them (lists, multi-hop)
    topic   = best_topic(query, facts)                    # with its small, medium and big summaries

    # 2. ONE round of Jev questions, all in parallel (free, ~1-3 s)
    intent  = jev.choice(query, ["overview", "single_fact", "list", "when", "exact_value"])      # G9
    enough  = {lvl: jev.noul("does this summary alone answer?", query, topic[lvl])            # G10
               for lvl in ("small", "medium", "big")}
    for item in facts + about + msgs:                                                          # G11
        item.relevant = jev.noul("is this memory about the question's subject?", query, item)
        item.usable   = jev.noul("is this memory part of the answer?", query, item)

    # 3. the smallest context that answers
    if intent == "overview":                              # the small -> medium -> big ladder
        for lvl in ("small", "medium", "big"):
            if enough[lvl] >= summary_min_probability:
                return topic[lvl]
    cap  = 40 if intent == "list" else 12                 # lists keep every useful item
    kept = sorted([i for i in candidates if i.usable >= item_min_probability], key=usable)[:cap]
    if intent != "overview" and jev.noul("does the evidence answer completely?", query, kept) < gate_min_probability:
        kept += on_topic_backups(candidates)[:12]         # G3: expand only when needed
    context = render(kept)                                # facts with quotes + original messages, dated
    if intent != "exact_value" and enough["small"] >= 0.3:
        context = one_line(topic["small"]) + context      # a line of orientation (R15: never for exact values)
    mark_stale_facts(kept); attach_replacements(kept)     # R13, R6
    return trim(context, token_budget)                    # LoCoMo average: ~600 tokens

Code finds candidates cheaply; Jev, free and fast, decides which of them belong in the context. Overview questions get the smallest summary that answers (the small, medium, big ladder); every other question gets only the facts and original messages Jev judged to be part of the answer. Stale facts are still returned, marked stale, and replaced facts show what replaced them. Earlier versions (v0.6 search-then-zoom, v0.7 evidence-first) are kept in the engine as recall_v06 and recall_v07.

5.4 Sleep

Runs for one session, from that session's watermark, while holding the memory lock. must steps always finish. defer steps stop when sleep_token_budget runs out and resume at the next sleep.

  1. Segment mustSplit the log from the watermark into episodes. Jev answers "boundary here?" for each pair of neighbouring windows. J
  2. Extract mustAn LLM lists the facts in each episode, with kind, source, evidence (log or code spans), entity mentions and validity start. Every claim is counted.
  3. Verify mustJev sees only the claim and its cited span: "does this support it?" Below judge_min_probability the question goes to an LLM. Failures are dropped and counted. J
  4. Link mustResolve each entity mention to an entity or a new one; attach each episode to a topic or a new one; label each new fact against its nearest neighbours. J
  5. Resolve mustFor each contradiction Jev chooses: newer replaces older (set valid_to), both true in different scopes (narrow the scopes), or older still valid (reject the new fact). Trust order decides ties. J
  6. Update topics deferMark touched topics dirty. Split a topic into chronological parts once it has more than topic_split_facts facts. Refresh each summary's keyword anchors from its facts (code, no LLM). Rebuild Big if any of its facts changed; Medium and Small only if a cited fact changed or Jev says the change matters at their size. Every sentence cites fact ids. J
  7. Roll up must / deferSession node: must. Periods for closed weeks, and core when due or on the first sleep: defer.
  8. Forget deferScore active nodes with the retention formula, using Jev's importance and surprise levels. Archive those under the threshold; parents keep their links. Never archive core, the latest period or user facts. J
  9. Wake note and export mustWrite open problems, plan and topics for the next session. Write memory.md. Release the lock.
Retention score
score = 0.35 * (importance - 1) / 4                # Jev score level 1..5
      + 0.25 * exp(-days_since(last_used) / 30)
      + 0.20 * min(1, log(1 + useful_count) / 3)   # usefulness, not raw recalls
      + 0.20 * (surprise - 1) / 3                  # Jev score level 1..4

archive if score < archive_threshold               # parents keep their links
never archive: core, latest period, source = user
unarchive on any recall hit

5.5 Nap

If context fills in the middle of a task, run steps 1 to 4 on the oldest nap_fraction of the context only, from the session's watermark. Move the watermark, replace that part of the context with the resulting episode text, and continue. The next full sleep starts from the watermark, so it never re-segments what the nap covered, and runs steps 5 to 9 over every episode made since the last full sleep.

5.6 Several sessions at once

  1. Each running session (terminal, worktree, agent) has its own session id, its own log stream and its own watermark.
  2. A session consolidates only its own log, when it sleeps. It takes the memory lock for the write part of sleep; other sessions keep reading.
  3. Facts carry scope.branch. Recall on another branch skips them until they are merged.
  4. When a branch merges, its facts are promoted to the main scope at the next sleep. When a branch is deleted unmerged, its facts are archived.
  5. If two sessions wrote contradicting facts, the next sleep's resolve step handles them like any other contradiction.
06

Jev: the fast decision layer

Decisions go to Jev. Writing goes to an LLM.

Jev from TypeSafe AI takes a block of state plus typed questions and returns a probability (noul), a pick from a list (choice) or an ordered level (score, 2 to 10 levels). It does not write text. Any step whose answer is one of a small, known set goes to Jev: as the gate while awake, and as the judge during sleep. Neither role writes memory; the consolidator does.

Shadow firstEach question starts in shadow mode: the LLM (or old rule) decides and Jev's answer is only logged. It goes live once it agrees on at least jev_promote_agreement of jev_promote_min_samples cases.
CalibrationOutcomes are recorded later (was the recall enough, did the verified fact hold up). Weekly, each question's threshold is tuned from its decision log.
FallbackBelow gate_min_probability (awake) or judge_min_probability (asleep), or after jev_timeout_ms, the question goes to an LLM. Awake defaults if that is too slow: recall yes, start at topic small.
LimitsHosted API only, a few hundred ms per call, text state only. Fine for routing and judging, not motor reflexes.

Not for Jev

Anything that writes textExtract, topic and time summaries, and the wake note stay with an LLM.
The redactorAsking a hosted API "is this a secret?" sends the secret out. Redaction stays local.
Hard thresholds and formulasContext share, idle time, token caps and the retention formula stay in code. Jev only feeds importance and surprise into the formula.
07

Rules

These hold at all times. An implementation that breaks one is a different architecture.

  1. R1
    The raw log is append-only.Rows are redacted locally before they are written, then never edited or reordered. The one exception is a privacy delete, which replaces a row's content with a tombstone and keeps its seq.
  2. R2
    Every fact cites evidence.Each fact has an id and at least one log, code or user span.
  3. R3
    Only verified facts are stored as facts.A claim that fails verification is dropped and counted, not kept at low confidence.
  4. R4
    Summaries are regenerated from their sources.Time nodes from their children, topic sizes from the topic's facts. Never by editing earlier text or shrinking a sibling size.
  5. R5
    Forgetting is not deleting.Archived nodes leave the index, stay in storage and stay reachable through their parents. The only true delete is the privacy path (R1).
  6. R6
    Superseded facts never surface alone.Recall returns the old fact together with the fact that replaced it, marked as superseded.
  7. R7
    Check evidence before acting.If a remembered fact will drive a decision, open its evidence first. If it was not checked, say so.
  8. R8
    Verify is independent of extract.A different model from the extractor (Jev qualifies), or at minimum a different prompt with no access to the extractor's reasoning.
  9. R9
    No consolidation while awake.Each session consolidates only its own log, only while it sleeps or naps. Recall bookkeeping is allowed while awake.
  10. R10
    Every summary sentence cites its sources.A sentence without fact or child ids fails the drift check.
  11. R11
    Trust order holds.CLAUDE.md, then user, then observed, then inferred. A lower-trust fact never silently replaces a higher-trust one; the conflict is flagged instead.
  12. R12
    Every Jev decision is logged.No Jev question goes live without passing shadow mode, and Jev never writes memory itself.
  13. R13
    Stale code evidence cannot drive a decision.If the cited code changed since its commit, read the current code first.
  14. R14
    One writer at a time.Shared memory is written only under the lock. Branch facts stay in their branch scope until merged.
  15. R15
    Exact values come from evidence.When a question asks for an exact value, recall may stop, and the answer may quote, only from fact evidence, anchors or the original log, never from a summary's wording.
  16. R16
    No fact is stored twice.A new fact that only restates a stored one is dropped. A different number, date, version, name, file, id or ordinal always makes it a new fact. (v0.9.5)
  17. R17
    Memory never learns from itself.Hypnos's own output (cleanup lists, wake notes, recalled memory) and memory or session housekeeping (/memory-cleanup, /deleate and the answers to them) are never logged. (v0.9.5)
  18. R18
    Coding memory keeps only what a later session needs.One-off steps, a tool's internals, counts from a single run and session titles are dropped before saving. What the user states is always kept. (v0.9.5)

Build order

  1. start here
    Log and baselinesLocal redactor, per-session raw log with watermarks, decision log, a test environment with known ground truth, flat-search and rolling-summary baselines.
  2. Tree, topics, entitiesEpisodes with typed, sourced facts; sessions; the topic ladder; entities; hybrid search; recall with fallback and trust order.
  3. Full sleepVerify, link, resolve with validity windows, incremental topic rebuilds, forget, sleep budget, memory.md export. Compare against the baselines.
  4. Jev
    Jev, shadow to liveRun all 17 questions in shadow. Promote them one by one. Start with J2 (verify) and G3 (sufficient), which save the most.
  5. coding
    Code-aware and multi-sessionCode evidence and staleness checks, coding fact kinds, CLAUDE.md on wake, the memory lock and branch scopes.

Out of scope for this version

weight updates from memory robot bodies multiple cooperating agents

Suggested stack: Python, SQLite (with FTS5 for BM25), sqlite-vec or FAISS, git for code evidence, any LLM API for writing, Jev for the gate and judge. A cheaper model can run extract.

What it showed at the time (v0.6)

v0.6 is the best system96% against keyword search's 90%, with no confident wrong answers, and 98% on the newest sessions where earlier versions struggled.
Evidence beats summariesThe exact-value rule stopped fluent summaries from passing as answers: 100% on every question answered at the small level.
Cheaper where it mattersThe hard 42% now read ~5,780 tokens instead of ~9,920, because the log steps no longer carry the big summaries.
Meaning search found what keywords missed"Consolidate service hosts" now finds SvcHostSplitThresholdInKB, which no earlier version answered.
Still more tokens than keyword search3,531 against 2,258 per answer, plus 0.78M to build. Against plain opencode it is about 10× cheaper.
Tuned on these questionsv0.6's fixes came from studying failures on these same 60 questions, so a fresh question set is needed to confirm the gain.

Caveats

  • Questions were written from the raw log text and graded against exact quotes; 59 of 60 ask for an exact value.
  • v0.6 was graded by Muse Spark 1.3 only: the 1.2 cross-check was failing on OpenCode's servers during this run. Earlier runs showed the two graders agreeing on 99% of grades.
  • v0.4 to v0.6 were designed after seeing earlier results on these same questions. Plain opencode covers 24 of the 60.
  • Reduced prototype: fixed-size episodes, no entities, trust order, validity windows or incremental rebuilds. One run.
